A secret is one `KEY → value`, encrypted at rest under `~/.adi/mono/secrets/`, injected as an
environment variable into an [[Agents|agent]]'s runs. The list view only ever shows names and
descriptions — a value crosses the wire solely on an explicit reveal, never on listing.

## Why it exists

An agent that calls an external API needs a credential somewhere. Pasting it into a prompt or a
tool's source puts it in a transcript, a diff, a log. A secret is encrypted on disk, decrypted
only into the environment of a run that was explicitly given it, and readable back out only by
an explicit reveal (`adi-mono secrets read NAME`) — the list view shows names and descriptions
only, never the value.

## Do it

List: `adi-mono secrets list`. Panel: `/extended/secrets`.

```bash
adi-mono secrets set GITHUB_TOKEN --description "for the release tool"
adi-mono secrets read GITHUB_TOKEN     # the value-returning primitive; no --reveal flag
```

Attaching a secret to an agent is a separate, explicit step — see [[Agents#Nothing is on by default]] — done the same way as enabling a [[Tools|tool]]: tick it on that agent's definition.

### A model key, end to end

The same shape covers an OpenAI or Anthropic key for a `harness:adi` [[models|backend]]: set the
secret, name it in the backend definition, then attach that secret to the agent that runs on it.

```bash
adi-mono secrets set ANTHROPIC_API_KEY --description "harness:adi backend"
adi-mono llm backends save my-anthropic --runtime harness:adi --provider anthropic \
  --api-key-env ANTHROPIC_API_KEY
```

See [[models#How the key is stored|how the key is stored]].

## Project vs global

A secret is either **global** (available everywhere) or filed under a [[Projects|project]]. A
project secret overrides a global one of the same name, but only for that project's runs — so
the same `GITHUB_TOKEN` name can point at a different value per client or per team, and a run in
project A never sees project B's version just because it shares the name.

## Encrypted at rest <Flags>Expert area</Flags>

A value is sealed with **XChaCha20-Poly1305** (a 256-bit key, a fresh random nonce per write, the
secret's own `scope/name` as additional authenticated data, so a ciphertext copied elsewhere
fails to decrypt rather than returning the wrong value). The key itself lives in a `0600` file,
`~/.adi/mono/secrets/.master-key`, generated the first time a secret is written and never
rotated automatically — set `ADI_SECRETS_KEY_FILE` to move it off a disk that gets backed up or
synced alongside the ciphertext.

## OAuth, without a cloud console <Flags>Enterprise interest</Flags>

A secret's value can come from an OAuth flow instead of being typed in, so nobody handles a raw
token by hand. On `/extended/secrets`, name the secret, switch its source to OAuth, pick a
provider (Google today — Gmail read/send/manage scopes, or any other Google API; GitHub the same
way), and authorize. No Google Cloud project or client credentials are needed on your side: the
flow runs through `oauth-router.withadi.dev`, a small router ADI runs that holds those client
credentials on your behalf, and the resulting token renews itself from its stored refresh token.
Request the least scope that does the job.

## Least privilege <Flags>Expert area</Flags>

`adi-mono secrets read` (and the `sys-secrets` tool) returns any secret's value to a
shell-capable agent — enable that broadly only if you mean to. The tighter default is the
per-agent allowlist: attach exactly the secrets a given agent needs, and only those arrive as
env vars in its runs — see [[Agents#Nothing is on by default]]. A project secret shadowing a
global of the same name is a feature, not a collision — name deliberately.
