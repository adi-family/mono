ADI design system

How the product looks and why. The product is a dense tool for people who run agents on their own machines. The design's job is to keep that density readable — not to decorate it.

Principles

Five decisions that every screen inherits. When a new screen looks wrong, one of these is usually being broken.

The transcript is the product

Everything else — sessions, agent panel, explorer — is chrome. Chrome sits on darker surfaces, in smaller and dimmer type, so the eye lands on what the agent said.

Density is honest

ADI shows a lot because a lot is happening. We don't hide information behind whitespace. We make it scannable with hierarchy: weight, color, and hairlines — not with boxes.

Mono means machine

Monospace is reserved for things a machine produced or will consume: paths, hashes, commands, model ids, config values. Labels, names, counts and dates are sans. If mono is everywhere, it means nothing.

One orange per screen

Orange marks the single most important action or state on a screen: send, save, update, running. Two oranges compete; three is noise. Everything else is grey.

Surfaces, not boxes

Grouping is done with background tone and 1px hairlines. Panels are flush to the edges. Cards are for things that are genuinely detachable — a dialog, a QR pairing block — not for every section.

Sentence case, always

No uppercase tracked labels. Section headers are small, grey, sentence case. Uppercase was our loudest AI-tell, and it made body text unreadable.

Mark

Three hexagons, one in front. The mark is monochrome by default and takes the current text color, with the two back shapes at 52% and 74% opacity. The colored version exists for the app icon and the landing only.

Usage

Minimum size 16px. Clear space around it equal to the height of the front hexagon. In the top bar it sits at 18px next to the wordmark adi in 15px semibold. It never gets a glow, a drop shadow, a gradient background, or an animation. It is not a mascot.

Color

A grey scale with one accent. Four surface levels do the structural work; three ink levels do the hierarchy. Semantic colors appear only as small dots and pills, never as fills.

Rules

Tabular numbers everywhere (font-feature-settings: "tnum"). Line length capped at 80 characters in the transcript and 64 in forms. Bold is 600, and it's for one phrase per paragraph at most — a verdict, a name — never for whole sentences.

Space & radius

A 4px scale. Inside components use 4–12; between elements 16–24; between sections 32–48. The app never uses more than 48 inside a panel; the landing never uses less than 64 between sections.

4 for inline code and seg-control items. 6 for buttons, inputs, list items — the default. 10 for cards and code blocks. Pill for tags, chips, status. Panels have no radius: they're flush.

Layout

App shell: 48px top bar · 248–272px left panel · fluid center · 316px right panel · 28px status bar. Content padding 20–32px. Forms center at 640px. Landing container 1200px, one left edge for nav, hero and every section.

Icons

One library: Lucide. Stroke 1.5, never 2. Sizes 14, 16, 20. The icon takes the color of the text beside it and is always labeled in the app. No filled variants, no duotone, nothing behind the icon.

Rules

The short list. Most of what made earlier screens look generated is on the right.

Do

  • Group with surface tone and hairlines
  • Put the transcript on the lightest surface
  • Use mono for paths, ids, commands, config values
  • Dim values that repeat in every row
  • Collapse tool calls; show the count and the tool
  • Round money to cents, tokens to one decimal
  • Show shortcuts and secondary actions on hover
  • Put row actions in a ⋯ menu

Don't

  • Uppercase tracked labels, anywhere
  • Cards inside cards, or a card around a table
  • Mono for names, counts, dates, labels
  • More than one orange fill per screen
  • Stat cards with big numbers in boxes
  • Orange outlines as a selected state
  • Gradients, glows, blurred blobs, drop shadows on flat UI
  • Repeat an action word per row ("Revoke", "Rename")
  • Animate the mark, or anything the user didn't trigger
  • Mix icon libraries, draw custom icons, or use filled/duotone variants

Prompt block

Paste this at the top of any prompt that asks Claude to build or change ADI UI. It's the same rules in the form the model follows best: constraints first, forbidden list explicit.

DESIGN CONSTRAINTS — ADI (follow exactly, do not "improve")

Fonts: Geist (UI), Geist Mono (paths, hashes, commands, ids, config values, model names — nothing else). Landing only: Bricolage Grotesque 500 for headlines.
Surfaces (dark): side #101010, page #161616, hover #1B1B1B, raise #1E1E1E, active #232323. Hairline white 7%, input border white 13%.
Ink: #ECEAE6 primary, #A9A6A0 secondary, #6F6C67 labels/meta, #D6D3CD mono.
Accent #E8532A — exactly one filled orange element per screen (the main action or the live state). Semantic ok #4CB77A / warn #E0A84B / err #E25C5C as 6px dots or pills only.
Spacing scale 4/8/12/16/24/32/48. Radius: 6 default, 4 inline, 10 cards & code, pill for tags. Panels flush, no radius, no border — separated by hairlines.
Type: page title 20–22px/600, section 15–17px/600, transcript 15.5px/1.6 max 80ch, UI 13.5–14px, labels 12px grey sentence case, tabular numbers.

Never: uppercase labels; nested cards; a card around a table; stat cards; orange outlines for selection; gradients, glows, blobs, shadows on flat UI; mono for names/counts/dates; repeated per-row action words; unprompted animation.
Always: transcript on the lightest surface; sidebars dimmer and smaller; repeated column values dimmed; tool calls collapsed to "N calls · Tool · command…"; row actions in a ⋯ menu; shortcuts on hover.
